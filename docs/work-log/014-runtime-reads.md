# 운영 조회와 전사 복구의 반복 작업 감소

## 배경과 범위

[이슈 #14](https://github.com/altius03/lecture-stt-pipeline/issues/14)는 PR #13을 병합한 `dev 3a9245b`에서 시작했다. 녹음 수와 영향이 함께 커지는 보관함·검증기 SQL, 감시와 복구에서의 파일 접근, 후처리 및 패널의 설정 읽기를 살폈다. Go와 Python의 독립 계획 검증, 원전사를 바꾸기 직전의 재확인처럼 입력 변경을 감지하기 위한 읽기는 유지했다.

## 변경 내용과 결정 근거

- 보관함은 기존 정렬 기준으로 페이지와 현재 작업을 먼저 결정한다. 해당 페이지의 검토 건수와 산출물 수만 묶어 조회하고, 전체 건수는 같은 SQLite 읽기 트랜잭션에서 구한다.
- 저장소 검증기는 각 녹음의 활성 작업에 선택된 엔진만 조인한다. 작업마다 선택된 엔진의 개수를 확인해 누락·중복과 보관 처리된 엔진을 구분한다.
- 감시기는 임시 이름을 먼저 거르고 한 번의 `lstat`로 파일 종류·크기·수정 시각을 읽는다. 준비된 파일의 마지막 정렬은 기존 방식으로 수행한다. 복구기는 정상적인 중단 작업을 검사한 TXT와 JSON으로 곧바로 품질을 판정한다. 쓰기 전 지문 검증과 일시적으로 파일이 사라진 복구 대기의 재시도 처리는 유지한다.
- 후처리는 활성 학기 파일에서 한 번 읽은 바이트로 과목 경로와 SHA-256을 구한다. 학기가 바뀌는 순간에도 서로 다른 파일 버전에서 경로와 지문이 선택되는 일이 없다. 패널의 알림 선택·옵션도 요청마다 한 번 읽은 자격증명 가용 여부를 공유한다.

## 측정 결과

동일한 임시 SQLite DB에 기준 커밋의 쿼리와 변경 쿼리를 실행해 반환 행 전체와 순서를 대조했다. 녹음 500건마다 작업과 검토 항목 1개, 산출물 6개를 만들고 보관 처리된 녹음·산출물, 현재 작업이 없는 녹음, 엔진 누락을 섞었다. SQLite progress handler를 100명령마다 호출해 얻은 근삿값이다.

| 측정 범위 | 기준 | 변경 후 |
|---|---:|---:|
| 보관함 페이지 SQL, 네 요청의 합계 | 344,700명령 | 112,300명령 |
| 검증기의 작업·엔진 SQL, 500건 합계 | 19,703,000명령 | 1,048,800명령 |
| 정상 중단 전사 한 건 복구, TXT / JSON 열기 | 2회 / 2회 | 1회 / 1회 |
| 후처리 큐 한 건 등록, 활성 학기 파일 열기 | 2회 | 1회 |

보관함의 요청은 앞·중간·마지막 부분 페이지와 크기 0 페이지였으며 합계 113행이 양쪽에서 일치했다. 검증기는 500행이 일치했다. SQL 명령 수에는 전체 API 처리, 음성 추론, 운영 iCloud 지연이 포함되지 않는다.

## 검증

로컬 Python 전체 테스트, Python 컴파일과 `git diff --check`를 실행했다. 페이지 정렬 동률·전체 집계·빈 페이지, 보관 처리된 엔진, 학기 스냅샷 교체, 일시적 TXT 누락과 손상된 JSON이 겹치는 복구 대기 상태를 확인했다. GitHub 실행 결과는 이 PR의 Checks에서 확인한다. 운영 Mac mini 배포는 별도다.
